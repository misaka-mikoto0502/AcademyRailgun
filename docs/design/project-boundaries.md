# 炮姐模组开发边界与版本要求

角色能力与世界内容分开推进

整理日期 2026年10月21日。2026-10-22 的角色设计补充决定与待定项见 [角色讨论稿](character-design.md)，2026-10-21的历史进度见 [检查点](../checkpoints/2026-10-21.md)。本文继续约束版本与模块边界。

## 当前方向

项目分为角色与能力、世界内容两个部分。角色部分先建立自身玩法，世界部分后续增加实体、方块等内容。两部分分别安排里程碑与验证，基础体验不互相依赖，合装时再增加联动。

新项目面向 Minecraft Java 版1.20及以上。当前1.12.2整合包只作为旧玩法和实现思路的研究样本，不作为新 Mod 的开发或兼容目标。

| 项目 | 当前边界 |
| --- | --- |
| 版本下限 | Minecraft Java 版1.20及以上 |
| 第一部分 | 玩家角色 外观 能力 成长 操作界面 |
| 第二部分 | 新实体 方块 设备 材料 结构及世界内容 |
| 推进方式 | 角色部分先验证 世界部分后续独立实施 |
| 共同要求 | 职责明确 数据分开 基础进度不互锁 |

## 已确定与仍待选择

已确定版本下限、两部分拆分方向与控制首版体量。本轮进一步确认：可培养多名角色，当前选择一主一副，换搭配保留进度；各能力者的技能携带数量受限；主修深入、副修有限；成长结合原版资源、时间及部分使用或战斗条件。角色获取重视与原版进程结合的科技树。角色档位与玩家操控上限分开，用户倾向个人操控上限全局共用；每名角色仍需特定材料或条件解锁并单独培养。操控突破以科技与材料为主，采用铁阶段入门、主世界Lv4、跨维度Lv5、终局Lv6的四段节奏；已形成三版候选设计供比较，尚未进入玩法实现。

具体游戏小版本、加载器、角色名单、完整成长模型、技能图形式、科技节点、装置具体承载条件与外观、能力网络含义和发行方式仍未锁定。当前先进行设计问答，用户明确确认方案后再实现主题玩法。本稿不把先前十种玩法全部纳入开发范围；那些方案继续作为候选内容库。

本文中的模块职责、验收方法和候选版本排序是整理后的工程建议，不代表已完成代码实现。它补充并约束此前的玩法调研；涉及当前开发范围时，以本稿记录的最新用户要求为准。

## 两部分的职责

### 角色与能力部分

负责玩家的角色资料、可选外观、专属技能、能力资源、成长记录、解锁关系和操作界面。先在原版地形与原版生物上验证能力用途，不等待专属敌人、城市、研究设备或新矿物。

后续首个原型控制动作数量，贯通角色获取、选择、使用、成长和恢复，实际数量在设计确认后决定。已确认成长结合原版矿物等资源和时间投入，部分能力还需要实际使用或战斗；具体活动、材料和条件逐项讨论。获取角色所需的科技树与变身器不能依赖尚未实施的独立世界内容；所需制作内容的模块归属仍待细化。

“独立”指不依赖另一部分的专属内容。角色技能仍可攻击生物、生成临时弹射物、显示粒子或操作允许的方块；这些是技能所需实现，不必因为属于实体或方块 API 就划到第二部分。

### 世界内容部分

负责有独立世界用途的敌人、生物、NPC实体、材料、设备、方块、结构及其状态。新增什么内容应由玩法需求决定，不预设必须加入完整城市、大型工业链或大量首领。

独立使用时，基础目标应有普通装备、工具或配方入口。与角色部分合装后，可以增加特殊交互、技能应对与额外奖励，避免要求玩家选择指定角色才能推进基础内容。

### 跨部分内容如何归属

| 内容 | 角色部分负责 | 世界部分负责 |
| 人物作为 NPC 出场 | 人物设定 对话 关系规则 | 出场 位置 寻路 跟随与实体状态 |
| 技能命中新敌人 | 技能目标与效果规则 | 敌人行为 弱点与响应 |
| 设备辅助训练 | 接收合法成长结果 | 设备操作 资源与世界状态 |

跨部分功能通过联动适配实现。一方尚未完成时，可以用原版目标、界面或测试数据验证另一方，不把所有联合功能列为独立部分的交付前提。

## 独立推进与联动边界

### 代码与数据

角色部分管理角色、专精、技能和玩家能力状态；世界部分管理设备、结构、实体及事件实例。服务器各自校验操作并保存所属状态，联动只传递明确请求与结果。

双方通过稳定编号、标签、事件或窄接口交互，避免在基础逻辑中直接依赖对方具体实现类。可选内容引用必须有缺失时的处理；配方、奖励与界面也要随联动是否启用正确加载。

可以先在同一代码仓库内分模块组织，暂不建设大型通用框架。最终发布成两个独立 Mod，还是同一工程中的可选模块，需在验证加载与依赖边界后确定。如果要求玩家能够分别安装，构建产物也必须支持这种方式。

### 基础体验如何验收

| 运行组合 | 必须验证的结果 |
| 仅角色部分 | 能选择 使用能力 获得基础成长 死亡重生与重连后状态正确 |
| 仅世界部分 | 有普通玩法入口 无角色功能时不会缺类或卡住基础目标 |
| 两部分合装 | 联动只启用一次 不重复奖励 各自存档与规则保持一致 |

上述条件均需分别验证客户端与专用服务器。“不干扰”意味着没有不必要的硬依赖和异常传播；新增能力与敌人对平衡的影响仍需合装测试。独立安装也不等于加入世界内容后可以随时删除它而不影响原存档。

### 首版需要控制的范围

角色部分不以大量新增生物、方块和建筑作为起步条件。世界部分也不承担整个角色能力系统的实现。技能表现、物品转移、位移和新方块交互先采用有限规则，避免把自由物理模拟与任意机器搬运作为基础能力。

两部分采用一致的首发游戏版本和加载器，是本稿建议的工程约束。更新节奏可以不同，联动时记录双方兼容版本范围；首版不同时维护多个 Minecraft 分支。

## 游戏版本与加载器候选

用户要求的下限是 Minecraft Java 版1.20，而非必须停在1.20。当前先比较下面两条有明确资料和参考项目的路线；它们不代表对所有新版本的完整调查，也不把1.21.1称作当前最新版。

| 项目 | 候选路线一 | 候选路线二 |
| 游戏版本 | 1.21.1 | 1.20.1 |
| 加载器 | NeoForge | Forge |
| 开发环境 | 64位 JDK 21 | 64位 JDK 17 |
| 现有依据 | 版本化官方文档 参考 Mod 发布文件 | 官方文档 前期选定源码 参考 Mod 发布文件 |
| 选用条件 | 角色所需库与目标联动齐备且小样通过 | 明确需要此版本联动或现有参考能降低开发成本 |

两个 JDK 要求分别见官方入门文档。[S01][S02] 此处的路线顺序仅表示先考察较新的1.21.1，不是最终技术选型；1.20.1仍满足用户要求。

Create 作者文件页有1.21.1 NeoForge与1.20.1 Forge发布记录；Ars Nouveau 也列出相应目标文件。[S03][S04] 它们提供候选生态依据，不是本项目的必装清单，也不能据此保证联动运行或 API 稳定。

### 正式选型前验证什么

围绕首个角色原型核对输入、玩家数据、渲染、网络和实际需要的辅助库；再验证客户端启动、专用服务器启动、存档重启与必要联动。没有必要为尚未决定采用的大型内容 Mod 锁定版本。

首版最终只锁定一组明确的 Minecraft 小版本、加载器版本、JDK 和必要依赖。Forge 与 NeoForge 分别适配；不承诺同一 JAR 跨加载器运行，也不把“1.20以上”当作兼容所有后续版本的声明。

现有 Java 核心尚未连接 Minecraft。其 Java 8兼容字节码只是前期原型设置，后续游戏工程按选定平台的 JDK 与工具链建立，不再为了兼容旧整合包限制新实现。

## 下一步工作与资料依据

### 分阶段推进

第一阶段通过问答收敛角色体验、科技树获取、能力成长、主副搭配与外观规则。已确认方向记录在角色讨论稿，角色名单、技能数量和具体数值继续讨论。用户明确确认方案后，才进入后续实现阶段。

第二阶段围绕该原型完成版本小样验证，锁定一个平台，再接入玩家数据、输入、施放、存档与多人表现。完整模型、复杂技能树和全员角色不作为贯通流程的前提。

第三阶段在角色部分可以独立运行后，选择一个有独立用途的世界内容做切片。验证单独运行，再加入一项联动，检查双方职责是否真的分开。世界内容的概念与素材准备可以提前，正式功能不必同时铺开。

### 现在保留的选择空间

原作角色本人、自建能力者两种方向继续保留。已允许培养多名角色并更换搭配保留进度；更换条件、皮肤覆盖还是服装、等级与技能图形式、网络玩法规模，以及是否加入伙伴 NPC 仍未固定。抽卡和随机词条留待后续讨论，抽卡不作为角色获取的主要方式。十种玩法按需要拆成角色侧、世界侧与联动内容，逐项选择，不整体承诺开发。
