## 截止此处的设计决定

| 事项 | 已确认内容 |
| --- | --- |
| 推进方式 | 通过对话逐步确定设计，用户明确确认方案后再实现 |
| 总边界 | Minecraft Java 版至少 1.20；角色能力与世界内容独立推进 |
| 体验目标 | 玩得爽、长期有内容、自由度、创造性和连携，避免无谓限制 |
| 培养与搭配 | 可培养多名角色，当前选择一主一副；换搭配保留进度 |
| 携带限制 | 每名能力者可携带的技能数量有限，数值待定 |
| 主副深度 | 主修深入发展，副修只能掌握其他体系的有限部分 |
| 成长 | 角色与技能均需培养；结合资源、时间，部分需要实际使用或战斗 |
| 能力用途 | 战斗之外也服务于探索、生存、建造等活动 |
| 角色获取 | 以与原版资源、世界或怪物推进相结合的严格科技树为重要主线，最终掌握某些角色的变身器 |
| 随机扩展 | 抽卡和随机词条留待后续讨论；抽卡不作为角色获取的主要方式 |

具体措辞、建议与待定项见 [角色设计讨论稿](../design/character-design.md)。原作角色身份与自建能力者两个方向都保留，尚未确定外观和玩法怎样对应。

## 对话推进顺序

1. 了解工程现状，确认只有规则原型和平台小样，尚未接入主题玩法。
2. 开始问答式设计，讨论扮演原作角色与自建能力者，两种方向均保留。
3. 用户提出来自两名能力者的技能搭配，并限制每名能力者的携带数量。
4. 确认主修深入、副修有限，以及角色培养、技能升级、多种成长来源和非战斗用途。
5. 用户选择开放培养名单，每次选择一主一副，更换搭配保留培养进度。
6. 提出抽卡与随机词条作为长期可玩性扩展，随后要求延后讨论。
7. 用户明确角色获取更重视与原版进程结合的科技树，以及最终获得变身器。
8. 助手询问变身器是解锁凭证还是持续装备；用户尚未回答，先要求保存今天的检查点。
