# 学习结果对本项目的影响

记录日期：2026-10-21。本篇是对当前原型的复查与后续工程建议，不是玩法定稿。

## 1. 当前原型可以提供什么

本地 `AbilityEngine` 可以验证一部分纯规则流程；`Catalog` 可以校验定义关系；`PlayerState` 和 Snapshot 将实例状态与内容定义分开；`GameAdapters` 给存档、时间、展示和技能行为预留了契约。

这些代码没有 Minecraft 类型，也没有加载器入口，适合作为讨论和规则验证的样本。以后可以保留、改造或替换；目录已经存在不构成必须沿用它的理由。

## 2. 正式接入前应补齐的边界

| 观察到的原型边界 | 后续要解决什么 |
| --- | --- |
| `cast` 只接收玩家状态、技能 ID 和 tick | 增加由服务端构建的有类型上下文：世界、目标、输入阶段、会话身份 |
| `AbilityBehavior.prepare` 的纯函数要求依靠约定 | 防止回调绕过检查修改状态；明确哪些能力能够访问游戏对象 |
| 核心扣费后返回 EffectIntent | 定义世界结算失败、重复消费和补偿策略，不能宣称跨系统原子性 |
| 资源是通用整数余额，成本为固定 Map | 按需要增加有边界的资源变更计划；数值精度、过载和动态成本后续决定 |
| 硬前置是全部满足式关系 | 将来需要 OR、互斥或条件解锁时扩展表达式，避免把它当成最终能力网络形式 |
| 释放是一次提交 | 持续、蓄力、取消、切维度和目标失效需要独立会话生命周期 |
| Snapshot 可以重建状态 | 增加磁盘格式、实际 schema 字段、迁移和错误恢复；内存重建不是存档验证 |
| Clock 是接口，调用者传入 tick | 明确所有玩家和维度使用的统一时间语义及重启恢复方式 |
| ID 与参数使用通用字符串 | 游戏接口使用有类型的输入，并限制长度、数量、深度和数值范围 |
| 每次操作创建快照 | 接入 tick 热点后测量分配量，按实际性能调整，暂不预先优化 |

本轮只记录这些差距，没有修改原型的玩法规则。

## 3. 三种“网络”分别讨论

1. 解锁依赖关系：节点是技能，边表示学习条件。
2. 运行中的能力联系：节点可能是玩家、效果或设备，边表示连接、共享或作用关系。
3. 客户端与服务端通信：消息、方向、协议和状态同步。

它们可以相互配合，但图约束、生命周期和数据结构不同。Create、AE2 的案例提供运行网络的研究方向，不自动决定动漫中“能力网络”在本项目里是什么玩法。[源码案例](05-mod-source-cases.md)

## 4. 内容定义与运行实例分开

未来可按需要分别表达能力定义、角色资料、玩家进度、临时执行会话和可见效果。资料可带展示键、行为类型和条件，执行器负责运行；角色资料不必成为所有业务逻辑的巨大父类。

原作设定可以提供内容参考，而数值与流程还需要适应游戏。角色数量、选择时机、成长来源、外观和最终技能表现仍然保持开放。

## 5. 选定平台后的最小验证顺序

| 步骤 | 观察到什么才算通过 |
| --- | --- |
| 环境 | 固定版本组合可以从 Wrapper 构建，而非依赖未知全局工具 |
| 加载 | 最小模组在客户端和专用服务器分别加载 |
| 数据 | 一个合成字段在退出、重启、重生后按规则恢复 |
| 通信 | 服务端从实际发送者处理请求；被拒绝的请求不改变状态 |
| 执行 | 一个无动漫设定的合成能力可以开始、结算、取消和清理 |
| 观察 | 另一个客户端能正确看到公开状态，私有数据没有无差别广播 |
| 重载 | 错误资料不会把正在使用的定义替换成半成品 |
| 内容 | 最后填入讨论确定的角色、动作、音效和专属技能 |

这只是工程推进顺序，没有提前选择某个 MDK 或安装依赖。

## 6. 验证方法与当前完成度

纯 Java 场景验证适合检查资源和依赖等状态约束；GameTest 可以在游戏场景验证部分交互；专用服务器和双客户端用于发现两端与同步问题；存档样本用于迁移；画面和音效则需要实际观察。[Forge GameTest](https://docs.minecraftforge.net/en/1.20.1/misc/gametest/)、[开发与运行](https://docs.minecraftforge.net/en/1.20.1/gettingstarted/)

本轮完成的是文献阅读、关键源码观察和架构复查。还没有新的游戏实跑证据。下一次真正搭建目标 Forge 工程时，应以上表逐项取得证据，而不是把“框架编译通过”当作整个 Mod 已经可用。
